## 一、实验目的

本实验从应用层向网络层逐级下沉：手工构造 HTTP 与 SMTP 报文，观察协议文本结构与状态机；借助 netcat 与 telnet 体会传输层的连接抽象；用 tcpdump 与 Wireshark 解析 TCP 握手/挥手、IP 首部字段与 TTL 递减机制；最后以原始套接字自行构造 IPv4 首部发送数据报。目标是掌握协议语义、分层职责边界，以及基于报文的取证与错误定位方法。

## 三、程序结构与设计

### 3.1　实验技术路线

实验一包含五个子任务，其中前四项是"用手工方式观察协议"，第五项是"用代码构造协议"。二者的技术路线与产物如下：

| 子任务 | 手段 | 关键产物 | 对应小节 |
|---|---|---|---|
| 手工获取网页 | `telnet` + 手写请求行 | 服务端响应首部原文 | 6.1 |
| 手工发送邮件 | `openssl s_client` + SMTP 状态机 | 七阶段命令/应答记录、`queued as` 与收件箱实收、落盘邮件 | 6.2 |
| 监听与连接 | `nc -l` + `telnet` | 全双工字节流样本 | 6.3 |
| 抓包与解析 | `tcpdump` + Wireshark | 150 帧 pcap、握手/挥手/ICMP 证据 | 6.4 |
| 原始套接字 | 自写 `ip_raw.cc` | 手工 IP 首部 + 双端抓包对照 | 6.5 |

前四项不涉及编程，第五项需要一个独立可执行程序。为使"程序结构与设计"一章言之有物，以下三节集中说明 `ip_raw.cc` 的设计。

### 3.2　`ip_raw.cc` 的模块结构

程序按"解析参数 → 确定地址 → 申请套接字 → 循环组包发送"四段式组织，各函数职责单一，避免把套接字操作与格式化输出混在一起：

| 函数 | 职责 | 关键点 |
|---|---|---|
| `parse_args` | 解析 `-n/-l/-t/-p/-i/-s` 与目的地址 | 非法输入抛 `invalid_argument`，而非静默取默认值 |
| `probe_source_addr` | UDP `connect` + `getsockname` 探测本机出口地址 | UDP `connect` 不发包，只触发一次路由查询 |
| `checksum16` | 16 位反码和，RFC 1071 | 纯函数，不依赖任何全局状态 |
| `dump_hex` | 以 4 字节一组打印首部十六进制 | 便于与抓包逐字节比对 |
| `print_header` | 逐字段解释首部 | 与 3.3 节字段表一一对应 |
| `main` | 组包、算校验和、`sendto`、错误分支 | 发送失败时区分 `EPERM` 与 `EMSGSIZE` |

选择"函数 + 局部结构体"而不定义类，是因为全部状态都在 `main` 的一次执行内，无需跨调用持有；引入类只会增加 `-Weffc++` 的初始化负担而无收益。

### 3.3　关键数据结构：IPv4 首部

首部用 `#pragma pack(push, 1)` 强制 1 字节对齐，并以 `static_assert` 保证 `sizeof` 恰为 20 字节，使内存布局与线上格式逐字节对应：

| 偏移 | 字段 | 长度 | 本实验取值 | 依据与易错点 |
|---|---|---|---|---|
| 0 | 版本 + 首部长度 | 1 | `0x45` | 高 4 位版本 4，低 4 位 5（单位 4 字节）。误写 `0x40` 则首部长度变 0，报文被丢弃 |
| 1 | 区分服务 TOS | 1 | `0x00` | 未启用 QoS |
| 2–3 | 总长度 | 2 | 52 | **必须含首部**且为网络字节序；内核有一致性校验（见 5.5） |
| 4–5 | 标识 | 2 | 进程号低 16 位起递增 | 同一数据报的各分片共享；本实验用它区分报文 |
| 6–7 | 标志 + 片偏移 | 2 | `0x0000` | DF=0、MF=0、偏移 0，允许分片 |
| 8 | 生存时间 | 1 | 64 | 由发送方设定，同一广播域内不减 |
| 9 | 协议号 | 1 | 253（`0xfd`） | **不可用 6/17**，否则被内核按 TCP/UDP 处理 |
| 10–11 | 首部校验和 | 2 | 计算后回填 | 计算前必须置 0 |
| 12–15 | 源地址 | 4 | 10.9.9.1 | 由探测得到，不硬编码 |
| 16–19 | 目的地址 | 4 | 10.9.9.2 | 命令行参数经 `inet_pton` 转换 |

一个设计判断需要说明：**不能把 `std::vector<uint8_t>` 的缓冲区强转成 `IpHeader*`**。`vector<uint8_t>` 只保证 1 字节对齐，而首部含 `uint16_t`/`uint32_t` 成员；在 x86 上非对齐访问仅降低性能，在 ARM 等严格对齐平台上会直接触发异常。因此程序采用"对齐的局部对象 `IpHeader ip{}` 填好后 `memcpy` 进缓冲区"的方式，代价是一次 20 字节复制，换来平台无关性。

### 3.4　核心算法：16 位反码和校验和

IP 首部校验和只覆盖 20 字节首部，不覆盖载荷——首部错了整包丢弃，载荷错了交给上层自行校验（TCP/UDP 各自有校验和）。这正是"IP 层尽力而为"的一个具体侧面。

算法分四步：按 16 位大端切字累加 → 奇数长度末字节补高位 → 进位回卷至不再溢出 → 按位取反。

```cpp
static uint16_t checksum16( const void* data, size_t len )
{
  const auto* bytes = static_cast<const uint8_t*>( data );
  uint32_t sum = 0;
  for ( size_t i = 0; i + 1 < len; i += 2 )              // ① 16 位大端切字累加
    sum += ( static_cast<uint32_t>( bytes[i] ) << 8 ) | bytes[i + 1];
  if ( ( len & 1U ) != 0U )                              // ② 奇数长度末字节补高位
    sum += static_cast<uint32_t>( bytes[len - 1] ) << 8;
  while ( ( sum >> 16 ) != 0U )                          // ③ 进位回卷至不再溢出
    sum = ( sum & 0xFFFFU ) + ( sum >> 16 );
  return static_cast<uint16_t>( ~sum & 0xFFFFU );        // ④ 按位取反
}
```

此处有一处极易自相矛盾的判据必须讲清：**本函数返回的是取反后的值，因此对"含校验和的完整首部"再算一次，结果应为 `0x0000`，而非 `0xFFFF`。** `0xFFFF` 是"返回未取反累加和"那种写法的判据。两种写法都正确，但同一份报告必须始终用同一种，否则前后打架。

### 3.5　发送流程

每个报文的构造顺序是固定的，顺序错了结果就错：

1. 用 `IpHeader ip{}` 值初始化，保证所有字节为 0（无残留）；
2. 逐字段赋值，其中 `check` 显式置 0；
3. 填充载荷文本（`CS144-Minnow ip_raw proto=253 seq=n/m`）；
4. 调用 `checksum16(&ip, 20)` 并把结果 `htons` 后写回 `check`；
5. `memcpy` 到报文缓冲区，与载荷拼成完整数据报；
6. `sendto` 发送，随后打印首部十六进制供人工比对。

第 4 步与第 6 步之间不做任何修改字段的操作——这是"打印出来的首部"与"线上首部"逐字节一致的前提，也是 6.5 节双端对照能够成立的原因。

## 四、方案对比

实验过程中有三处需要做方案取舍，以下逐一比较，并说明最终选择及其代价。

### 4.1　SMTP：公网服务商 vs 本地 `smtp-sink`

| 维度 | 公网（QQ 邮箱 SMTP） | 本地 `smtp-sink` |
|---|---|---|
| 可用性 | 前三轮 535，第四轮打通 | 一次成功 |
| 认证负担 | 需 SASL（`AUTH LOGIN`）+ 授权码 | 无认证，直接进入会话 |
| 可控性 | 服务端内部行为不可见 | 可加 `-v` 打印会话、加 `-d` 转储邮件 |
| 证据强度 | `235` + `250 queued as` + 收件箱实收，三层可互相印证 | 可同时证明协议对话、信封参数、正文落盘 |
| 真实性 | 真实生产环境，含 TLS 与认证 | 模拟服务端，不涉及跨网投递 |

**两者最终都保留，但承担的验证目标不同。** 公网方案覆盖的是"跨主机投递"——这一点 `smtp-sink` 无论如何替代不了，因为本地 sink 没有 MX 解析、没有中继、没有对方邮箱；本地 `smtp-sink` 覆盖的是"信封与正文分离"与"服务端落盘行为"，它不受网络与账号状态影响，可以随时重跑，且 `-d` 转储会把 `X-Mail-Args` / `X-Rcpt-Args` 显式写出来，是公网服务端不给看的内部视图。

过程中曾因前三轮 535 判定公网不可用、单方面改用 `smtp-sink`，第四轮打通后两者并存。这个反复本身是有价值的：**"换一条路"和"走通这条路"不是互斥选项**，前者用来保证实验能交付，后者用来保证结论完整。

### 4.2　抓包点：宿主机 Wireshark vs 虚拟机内 netns 对端

| 维度 | 宿主机 Wireshark 抓 VMnet8 | 虚拟机内 netns + veth |
|---|---|---|
| 可行性 | Npcap 驱动安装失败（错误 0x800700b7） | 内核原生支持，一次成功 |
| 抓包点性质 | 经 NAT 转换后的视角 | 发送端与接收端**各自独立协议栈** |
| 能否看到对端处理行为 | 不能，只看到过路报文 | 能，对端会回 ICMP 协议不可达 |
| 时间对齐 | 需人工对齐两个系统时钟 | 同一时钟，天然对齐 |
| 证据强度 | 中等（单一视角） | 高（双端逐字节对照 + 差错报文） |

选择 netns 方案。这不是退而求其次：**回环口抓包看不到链路层，宿主机抓包看不到对端协议栈的处理，而 netns 对端有自己的 ARP 表、路由表与 IP 标识计数器，是一个真正的"另一台主机"**。它唯一的局限是与发送端共用一个内核，无法模拟物理链路故障。

### 4.3　双向字段对照：单点双向 vs 双点同时抓包

指导书要求"同一分组在发送方与接收方的字段对比表"。严格实现需在两个抓包点同时捕获同一个报文，本实验受条件限制（宿主机抓包不可用）只能单点抓包，故有两案：

| 维度 | A：同一连接双向对照 | B：双点同时抓包 |
|---|---|---|
| 可行性 | 5 分钟，仅需既有 pcap | 需宿主机抓包，本环境不可用 |
| 是否满足"同一分组" | 不满足，是同一连接的两个方向 | 满足 |
| 证据强度 | 可逐项解释方向性差异（TTL/DF/地址互换） | 理论上更强，但 NAT 会改写字段，反而不易解释 |
| 附加发现 | 由标识连号定位到"回包被宿主机重建" | 难以察觉该问题 |

选择 A，并在 6.4.4 节明确写出"抓包点仅一处"这一限制。事后看这个选择带来了意外收获：正是在逐项比对双向字段时，才发现远端与网关的 IP 标识连号，从而定位到 TTL=128 的真正成因（6.4.5 节）。若采用双点方案，两个抓包点的 TTL 都会被宿主机栈改写为同一个值，反而看不出异常。

## 五、实现难点

以下七处是本次实验实际卡住或几乎卡住的地方，按"现象—原因—处理"记录。

### 5.1　缺一个空行，HTTP 请求超时

首次手工请求时只发了请求行与两个首部便等待响应，服务端返回 `408 Request Time-out`。原因是 HTTP 用**独立的 CRLF 空行**标志首部区结束，缺它服务器无法判断请求边界，只能一直等。处理：显式多按一次回车。这条比任何文字解释都能说明"空行是一个字节序列而非排版"。

### 5.2　SMTP 会话全部成功，却找不到邮件

`smtp-sink` 连跑两轮、会话日志显示 `msg=1`，但 `~/smtp_mail` 为空。查阅手册首句即写明其设计目的是性能压测——**收下邮件后直接丢弃**，必须显式加 `-d <模板>` 才落盘。处理：加 `-d` 并把端口改为 2525（免 sudo，文件属主即本人）。

### 5.3　`vector` 缓冲区不可强转为首部结构体

初版用 `reinterpret_cast<IpHeader*>(packet.data())` 直接写字段，在 x86 上能跑，但 `vector<uint8_t>` 只保证 1 字节对齐。处理：改为对齐的局部对象填好后 `memcpy`，并在 3.3 节把这个判断写成显式设计约束。

### 5.4　校验和的自洽判据究竟是 `0x0000` 还是 `0xFFFF`

查阅资料时两种说法并存，一度怀疑实现有误。根因是"函数返回取反值"与"返回未取反累加和"两种写法各有其判据：前者整首部再算得 `0x0000`，后者得 `0xFFFF`。处理：明确本实现属于前者，并用 `capture.pcap` 帧 74 的真实首部回归验证——清零重算得 `0xbb50`，与抓包值完全一致。

### 5.5　总长度填错会直接发送失败

Linux `raw_send_hdrinc()` 中有 `if (iph->tot_len != htons(length)) return -EINVAL;` 的一致性检查，`tot_len` 不含首部或未转网络序都会导致 `sendto` 失败。处理：`tot_len` 统一由 `IP_HEADER_LEN + payload_len` 计算，不做手工硬编码。

### 5.6　`ping` 远端回包 TTL=128 的假象

跨太平洋 RTT 170 ms，TTL 却是 128，二者不可能同时成立。起初误判为"Clash 代理导致"，进一步核查发现直连 Canonical 的报文回包同样为 128，且其 IP 标识与本地网关严格连号（`0xdef3`→`0xdef7`）。真正原因是 **VMware NAT + 宿主机 Windows 栈对所有回包统一重建**，TTL 被重置为 Windows 默认值 128、标识由同一计数器分配。处理：放弃"回包 TTL 相减推算跳数"，改用 traceroute 的主动 TTL 设定与首跳 ICMP 差错作为证据（6.4.5 节）。

### 5.7　框架的 `-Weffc++ -Werror` 让成员未初始化成为编译错误

自定义 `Options` 结构体中 `std::string` 成员未写初始化器，编译直接失败：`'Options::target' should be initialized in the member initialization list`。原因是 CS144 框架在 `etc/cflags.cmake` 中启用了 `-Weffc++`，该规则要求所有成员显式初始化。处理：全部成员改用 NSDMI（`string target {};`）。此事的启示是：**编译器的严格模式会把"风格问题"升级为"正确性问题"**，这在工程上是有益的。

### 5.8　`openssl s_client` 的 TLS 重协商陷阱

这个坑卡住了 SMTP 环节最关键的一步，且两次报错码不同，容易被误判为"服务器拒绝"。

**现象一**：`DATA` 阶段前突然打印 `RENEGOTIATING`，随后 `error:0A00010A:SSL routines:can_renegotiate:wrong ssl version`，连接中断。此时 `RCPT TO` 已返回 `250 OK`，说明命令本身没问题。

**现象二**：加上 `-tls1_2` 后错误码变为 `error:0A000153:ssl3_read_bytes:no renegotiation`，仍然中断。

**原因有两层**：一是 TLS 1.3 在协议层面**取消了对重协商的支持**，服务器一发起就报 `wrong ssl version`；二是退到 TLS 1.2 后，OpenSSL 3 默认设置了 `SSL_OP_NO_RENEGOTIATION`，于是报 `no renegotiation`。两条路都被堵死，说明**不是服务端的问题，是客户端实现的选择**。真正的触发条件是**输入方式**：整段粘贴时 `s_client` 边读标准输入边写网络，会在服务端尚未回 `354` 之前继续投递后续行，正好撞上服务器在 `DATA` 阶段发起的重协商。

**处理**：去掉 `-tls1_2`，恢复默认协商，并改为**逐行输入、每行等应答出现再敲下一行**，一次通过（6.2.2 节）。这件事说明：交互式协议调试工具的输出顺序本身就是信息，**把交互过程当成批处理来用，会丢掉"等待应答"这个隐含的同步点**。

## 六、测试与结果

### 6.1　手工获取网页（5.3.1）

先用浏览器访问 `http://cs144.keithw.org/hello` 作为对照组，页面正文为 `Hello, CS144!`（图 01）。由于目标站点位于境外且直连不稳定，终端侧通过 `proxychains4` 将 TCP 连接经宿主机代理转发，配置为 `socks5 192.168.159.1 7897`，代理链状态显示 `Strict chain … OK`（图 02）。

随后执行 `proxychains4 telnet cs144.keithw.org 80` 建立到 80 端口的字节流连接，逐行输入以下三条命令并**额外按一次回车发送空行**：

```
GET /hello HTTP/1.1
Host: cs144.keithw.org
Connection: close
（空行）
```

服务端返回完整响应（图 03），抓包还原的报文原文如下（帧 49、51、53）：

```
HTTP/1.1 200 OK
Date: Tue, 24 Nov 2026 06:44:26 GMT
Server: Apache/2.4.66 (Ubuntu)
Last-Modified: Thu, 13 Dec 2018 15:45:29 GMT
ETag: "e-57ce9343a1840"
Accept-Ranges: bytes
Content-Length: 14
Connection: close
Content-Type: text/plain

Hello, CS144!
```

浏览器渲染结果与手工请求的响应正文完全一致，说明浏览器在应用层并未做任何"魔法"——它发出的也是同样结构的文本报文，差异仅在于浏览器会自动补全 `User-Agent`、`Accept`、`Accept-Encoding` 等首部，并对正文按 `Content-Type` 渲染。

**响应首部各字段作用：**

| 字段 | 本例取值 | 作用 |
|---|---|---|
| 状态行 | `HTTP/1.1 200 OK` | 协议版本 + 三位状态码 + 原因短语。200 表示请求成功，是最常见的一类 2xx 响应 |
| `Date` | `Tue, 24 Nov 2026 06:44:26 GMT` | 服务器生成响应的时间（GMT），用于缓存新鲜度判定 |
| `Server` | `Apache/2.4.66 (Ubuntu)` | 服务端软件与版本，便于运维排查（也是信息泄露面） |
| `Last-Modified` | `Thu, 13 Dec 2018 15:45:29 GMT` | 资源最后修改时间，配合 `If-Modified-Since` 实现条件请求与 304 |
| `ETag` | `"e-57ce9343a1840"` | 资源实体标签，比时间戳更精确的缓存校验依据 |
| `Accept-Ranges` | `bytes` | 声明支持按字节范围请求（断点续传、分片下载） |
| `Content-Length` | `14` | 正文长度（字节）。`Hello, CS144!` 恰为 14 字节，是**定长**报文体边界的判定依据 |
| `Connection` | `close` | 指示本次响应后关闭连接，非持久连接 |
| `Content-Type` | `text/plain` | 正文媒体类型与字符集，决定客户端的解析与渲染方式 |

**关于"卡住"的教训**见 5.1 节：缺失空行导致 `408`，印证了指导书 5.2 节"空行是首部区结束的唯一标志"。

### 6.2　手工发送邮件（5.3.2）

#### 6.2.1　前三轮失败：535 认证被拒与一次错误归因

最初计划直接使用 QQ 邮箱 SMTP 服务。先在邮箱设置中开启 POP3/IMAP/SMTP 服务并生成授权码（图 05），确认服务已启用，随后进行三轮尝试：

- **第一轮**：`telnet smtp.qq.com 25`，经 `EHLO` 协商后使用 `AUTH LOGIN`，在 `334` 提示下提交 base64 编码的账号与授权码，返回 `535 Error: authentication failed`。
- **第二轮**：核对发现首次抄录的授权码仅 15 位（应为 16 位），重新生成后重试，**仍返回 535**。
- **第三轮**：改用 Python `smtplib.SMTP_SSL` 连接 465 端口，并用 Python 对自建的 `AUTH PLAIN` 字符串做 base64 解码校验，确认编码无误后提交，返回 `535 Login fail. Account is abnormal, service is not open, password is incorrect, login frequency limited, or system is busy.`；随即改用 `AUTH LOGIN`，连接被服务端直接断开（`SMTPServerDisconnected`）（图 04）。

三轮失败当时可排除的是**客户端写法**：TLS 握手成功、`EHLO` 能力协商完整（`250-PIPELINING` / `8BITMIME` / `AUTH LOGIN PLAIN`）、base64 编码经解码验证无误、邮箱服务确已开启。据此当时把 535 归因为**服务商侧的账号风控**——新账号、虚拟机 NAT 出口 IP 与常用登录地不一致、短时间内频繁认证，都可能触发限流。

**这个归因后来被证明是错的**，见 6.2.2。教训留在这里：535 是一个"多因一果"的状态码，服务端应答原文本身就并列列出了 `password is incorrect` 与 `login frequency limited` 两种可能，在拿不到服务端日志的前提下，仅靠排除客户端并不能确定成因。

#### 6.2.2　第四轮：SMTPS 打通，端到端投递成功

改用 465 端口（隐含 TLS，不是 `STARTTLS`），并**逐行输入、每行等应答出现后再敲下一行**（原因见 5.8 节）：

```bash
openssl s_client -connect smtp.qq.com:465 -crlf -quiet
```

完整会话（图 40）：

| 阶段 | 客户端发送 | 服务端应答 | 状态码含义 |

| 服务就绪 | （TCP + TLS 握手） | `220 newxmmxsp…qq.com XMail Esmtp QQ Mail Server` | 220 服务就绪；上方同时打印证书链 `depth=0/1/2`，根为 DigiCert Global Root G5 |
| 能力协商 | `EHLO localhost` | `250-PIPELINING` / `250-SIZE 73400320` / `250-AUTH LOGIN PLAIN XOAUTH XOAUTH2` / `250-MAILCOMPRESS` / `250-SMTPUTF8` / `250 8BITMIME` | `SMTPUTF8` 与 `8BITMIME` 是后文中文主题能被接受的前提 |

| 提交账号 | 账号的 base64 | `334 UGFzc3dvcmQ6` | 同上，对应 `Password:` |

| 结束会话 | `QUIT` | `221 … Bye` | 会话正常终止 |

**投递闭环确认**（图 41）：`mail.qq.com` 收件箱实际收到该邮件，主题「计算机网络实验一-手工SMTP邮件测试」，发件人显示「李 <3466786940@qq.com>」，时间 2026-11-24 17:03，正文与提交内容一致。至此"协议层接受（`queued as`）"与"用户层可见（收件箱）"两个层面同时成立，**跨主机投递真正打通**。

**前三轮失败而本轮成功，差异有三处**，按影响排序：

1. **授权码状态（决定性）**。前三轮所用编码均生成于多次认证失败之后。QQ 邮箱在连续登录失败后会作废此前生成的授权码，此时位数虽对、字符已失效，服务端仍答 535。第四轮使用重新生成的新码，一次通过。这正是 6.2.1 归因错误的来源——"码已作废"与"账号被风控"在应答文本上完全无法区分。
2. **端口与传输方式**。第一、二轮走 25 端口明文，部分前端机对未加密会话中的认证更严格；第四轮走 465 隐含 TLS，凭据在加密信道内提交。
3. **输入时序**。整段粘贴会让 `s_client` 在服务端尚未回 `354` 时继续投递后续行，与服务器在 `DATA` 阶段发起的 TLS 重协商请求相撞而断链（详见 5.8 节）；逐行输入规避了这一窗口。

#### 6.2.3　对照验证：本地 `smtp-sink` 观察信封与落盘

作为公网方案的对照，另用 Postfix 自带的 `smtp-sink` 在本机 2525 端口搭建 SMTP 服务端，并加 `-d` 参数把投递事务转储到磁盘（图 06）。它的价值不在"替公网发信"，而在于**服务端的一切内部视图都可见**：会话日志、信封参数、落盘正文。

```bash
mkdir -p ~/smtp_mail

```

客户端 `telnet 127.0.0.1 2525` 后完整会话如下（图 07–09）：

| 阶段 | 客户端发送 | 服务端应答 | 状态码含义 |
|---|---|---|---|
| 建立连接 | （连接请求） | `220 smtp-sink ESMTP` | 220 服务就绪，可开始会话 |
| 能力协商 | `EHLO lwk.local` | `250-smtp-sink` / `250-PIPELINING` / `250-8BITMIME` / `250-AUTH LOGIN PLAIN` / `250 DSN` | 250 命令成功；多行应答用 `-` 续行、末行用空格结束 |
| 声明发件人 | `MAIL FROM:<lwk@example.com>` | `250 2.1.0 Ok` | 250 成功；`2.1.0` 为增强状态码，2 表示成功类 |
| 声明收件人 | `RCPT TO:<test@example.com>` | `250 2.1.5 Ok` | 250 成功，收件人有效 |

| 结束会话 | `QUIT` | `221 2.0.0 Bye` | 221 服务关闭信道，会话正常终止 |

**验证落盘**（图 10）：`~/smtp_mail/20261124-152515.4bf7a966`，306 字节，内容如下：

```
X-Client-Addr: 127.0.0.1
X-Client-Proto: ESMTP
X-Helo-Args: lwk.local
X-Mail-Args: from <lwk@example.com>
X-Rcpt-Args: to <test@example.com>

```

**这里体现的协议设计要点是"信封与正文分离"**：`MAIL FROM` / `RCPT TO` 构成信封（envelope），由传输层使用，决定投递路由；`Subject` 之后的才是正文（body），由最终用户阅读。服务端把两者分别记录为 `X-Mail-Args` / `X-Rcpt-Args` 与正文，正好把这层分离显式化——这一点是 HTTP"首部就是报文自身"所没有的。此外，`X-Client-Proto: ESMTP` 说明由于使用了 `EHLO` 而非 `HELO`，会话升级为扩展 SMTP；文件名后缀 `4bf7a966` 与 `Received` 行中的 id 一致，验证了 `-d` 模板的"strftime 展开 + 随机十六进制后缀"命名机制。

#### 6.4.1　TCP 建立与释放

**三次握手**（帧 131–133，图 21，本机 `127.0.0.1:51152` ↔ `9090`）：

| 帧 | 方向 | 标志位 | 含义 |
|---|---|---|---|
| 131 | 客户端 → 服务端 | `SYN=1, ACK=0` | 请求建立连接，携带初始序号 ISN(c) |
| 132 | 服务端 → 客户端 | `SYN=1, ACK=1` | 同意建立，携带 ISN(s) 并确认 ISN(c)+1 |
| 133 | 客户端 → 服务端 | `ACK=1, SYN=0` | 确认 ISN(s)+1，连接进入 ESTABLISHED |

三次而非两次的原因：双方各自需要一个"我的序号被对方收到"的确认，两次无法同时确认服务端的发送能力与客户端的接收能力，且会残留半开连接。

**四次挥手**（帧 140–142，图 23），实际只捕获到 **3 个报文**：

| 帧 | 标志位 | 含义 |
|---|---|---|
| 140 | `FIN=1, ACK=1` | 主动关闭方发送 FIN 并捎带对先前数据的确认 |
| 141 | `ACK=1` | 被动关闭方确认 FIN |
| 142 | `FIN=1, ACK=1` | 被动关闭方发送自己的 FIN 并捎带确认 |

理论上应有的 4 个报文中，**第二段的 ACK 与第三段的 FIN 被合并在同一报文**（延迟确认机制），因而观测到 3 段。这说明"四次挥手"是逻辑模型，实际报文数取决于实现是否启用捎带确认。

#### 6.4.2　HTTP 请求与响应

#### 6.4.4　IP 首部字段的双向对照

按 4.3 节的方案选择，抓包点仅设于虚拟机内部一处，无法实现"同一分组在收发两端"的双点捕获。为此选取一条**完整的直连 TCP 连接**作双向字段对照——本机 `192.168.159.128:43376` 与 `91.189.91.63:80`（Ubuntu 系统网络连通性检查 `connectivity-check.ubuntu.com`，帧 39–46，未经代理转发）：

| IP 首部字段 | 帧 42（请求方向） | 帧 44（应答方向） | 差异来源 |
|---|---|---|---|
| 版本 / 首部长度 | 4 / 20 字节（`0x45`） | 4 / 20 字节（`0x45`） | 相同，标准 20 字节首部 |
| 区分服务 TOS | `0x00` | `0x00` | 相同，均未启用 QoS |
| 总长度 | **127** | **119** | 载荷长度不同（请求 vs 响应） |
| 标识 Identification | **0x5c87**（23687） | **0xdef5**（57077） | 由各自协议栈独立分配，二者无关联 |
| 标志 / 片偏移 | **`0x4000`（DF=1）** | **`0x0000`（DF=0）** | 协议栈默认策略差异 |
| 生存时间 TTL | **64** | **128** | **系统初始值不同**（Linux 64 / Windows 128） |
| 协议号 | 6（TCP） | 6（TCP） | 相同 |
| 首部校验和 | **0xc6cc** | **0x4466** | 首部内容不同，须重算 |
| 源 / 目的地址 | `.128 → 91.189.91.63` | `91.189.91.63 → .128` | 方向相反，互换 |
| TCP 端口 | 43376 → 80 | 80 → 43376 | 同上 |
| TCP 标志 | `PA`（`0x18`） | `FPA`（`0x19`） | 推送数据 vs 推送并关闭 |
| 窗口大小 | 64240 | 64240 | 相同 |

**差异逐一解释：**

- **总长度**：IP 总长度 = 首部 20 + 载荷。请求载荷 107 字节、响应载荷 99 字节，故分别为 127 与 119。
- **标识**：IPv4 首部标识由发送方协议栈为每个数据报递增分配，用于分片重组。两端各自维护独立计数器，故无关联（这正是 6.4.5 节判定回包来源的关键切入点）。
- **DF 位**：Linux 在 TCP 连接上默认置 DF（`0x4000`）以启用路径 MTU 发现；Windows 默认不置（`0x0000`）。
- **TTL**：由发送方设定初始值，Linux 与 Windows 的默认值分别为 64 与 128。**该差异反映的是发送端操作系统不同，而非转发跳数不同。**
- **校验和**：IP 首部校验和仅覆盖 20 字节首部（不含载荷），采用 16 位反码求和后取反。首部中任一字段变化都必须重算——例如帧 39 与帧 41 同为本机发出、仅总长度（60 → 40）与标识（0x5c85 → 0x5c86）不同，校验和即由 `0xc711` 变为 `0xc724`。

**TTL 变化与校验和的定量关系：** TTL 位于首部第 5 字节，与第 6 字节（协议号）拼成一个 16 位字 `0x01XX`，故 **TTL 每减 1，该字减少 `0x0100`，校验和相应增加 `0x0100`**。以帧 74 首部实测验证：

| 假设 TTL 取值 | 重算所得首部校验和 |
|---|---|
| 1（实际值） | **0xbb50** ✅ 与抓包一致 |
| 0 | 0xbc50 |
| 2 | 0xba50 |
| 63 | 0x7d50 |
| 64 | 0x7c50 |

差值恒为 `±0x0100`，**这就是"路由器每转发一次、TTL 减 1 并重算校验和"的定量体现**。

#### 6.4.5　traceroute 与生存时间递减规律

**（1）发送端的主动设定。** 执行 `traceroute -I -m 8 114.114.114.114` 期间，抓包显示本机向 `114.114.114.114` 连续发出 ICMP 回显请求，其 IP 首部 TTL 依次为 1、2、3 …… 8，且**每个 TTL 值恰好对应 3 个报文**（帧 74–76 为 TTL=1，帧 77–79 为 TTL=2，……帧 98–100 为 TTL=8）。这与 traceroute 的探测策略完全吻合：对第 N 跳使用 TTL=N 的探测包，每跳重复 3 次以提高应答概率。由此可见，**TTL 并非网络随机产生，而是由发送方按探测意图显式写入**（图 28）。

**（2）转发端的减一与丢弃。** TTL=1 的三个探测包（帧 74、75、76，IP 标识依次为 `0xb963`、`0xb964`、`0xb965`）发出后，本机收到三条来自网关 `192.168.159.2` 的 ICMP 差错报文（帧 90、91、92，Type 11 / Code 0）。展开帧 90 可见其 ICMP 载荷中内嵌了一份原始数据报首部，其中 `Identification = 0xb963 (47459)`、`Time to Live = 1`，与帧 74 完全一致（图 29、图 30）；帧 91、92 亦分别对应 `0xb964`、`0xb965`。**标识字段的逐一对应，证明网关丢弃并嵌回的正是本机发出的那三个数据报**，即 TTL 在该路由器转发时被减为 0，触发丢弃并回送差错。

与此同时，TTL=2 至 TTL=8 的探测包均未收到任何差错应答，说明它们已被网关正常转发离开本地网段。**"TTL=1 全部丢弃、TTL≥2 全部通过"的分界线精确落在第一跳**，这正是 TTL 每经一台路由器减 1 的直接观测。

值得注意的是，帧 90 中**同时存在两个 TTL**：外层首部为 128（网关自身生成差错报文时所用值），内嵌首部为 1（被丢弃的原始包）。同一报文内两个 TTL 并存，恰好说明 TTL 是在转发环节被改写的。

**（3）环境限制与替代证据。** 按 5.6 节的排查，本环境的回包 TTL 不可用于推算跳数。对全部 150 个报文按源地址统计：本机发出的报文 TTL 恒为 64，而来自 NAT 网关 `192.168.159.2`、宿主机代理 `192.168.159.1` 以及远端 `91.189.91.63`、`185.125.190.58` 的**所有应答，TTL 一律为 128**。进一步比对 IP 标识字段发现：

| 帧 | 源地址 | 协议 | IP 标识 |
|---|---|---|---|
| 40 | 91.189.91.63（Canonical，英国） | TCP | `0xdef3`（57075） |
| 43 | 91.189.91.63 | TCP | `0xdef4`（57076） |
| 44 | 91.189.91.63 | TCP | `0xdef5`（57077） |
| 46 | 91.189.91.63 | TCP | `0xdef6`（57078） |
| **90** | **192.168.159.2（本地 NAT 网关）** | **ICMP** | **`0xdef7`（57079）** |

**来自英国的服务器与本地网关，报文标识竟严格连号**——两个独立的 IP 栈不可能共用同一计数器。结合"回程 DF=0 不符合 Linux 默认行为"这一点，三项独立证据共同表明：**所有回包均由宿主机 Windows 网络栈统一生成后送入虚拟机，原始跳数信息在该环节丢失。** 这既解释了 `traceroute` 仅观测到第一跳、其余各跳均为 `* * *` 的原因（图 18），也说明本实验不能以"回包 TTL 相减"推算路径长度，故改以"主动 TTL 设定 + 首跳 ICMP 差错报文"作为递减机制的观测依据。

图中实测还显示：`ping cs144.keithw.org` 三次全通、TTL=128、RTT 169–224 ms；而 `ping 114.114.114.114` 100% 丢包。境外主机可通而回包 TTL 为 128（跨太平洋至少十余跳，不可能出现该值），国内地址反而全丢，正与"回包经宿主机重建"的判断一致。

两端同时抓包后发送 3 个报文（图 35、35b），程序输出与抓包结果逐项对照如下：

|---|---|---|---|

#### 6.5.2　对端确认与逐字节比对

对端 `tcpdump -r` 显示三条 `IP 10.9.9.1 > 10.9.9.2: ip-proto-253 32`（图 37）。其中 `32` 正是载荷长度，与 `总长度 52 − 首部 20` 完全吻合，说明总长度字段填写正确；`ip-proto-253` 则说明对端把协议号识别为"未知协议 253"，未误判为 TCP 或 UDP。两端统计均为 `0 packets dropped by kernel`（图 36、36b），样本完整。

**更有说服力的是对端的反应**（图 38b）：发送侧抓到 3 条

```
IP 10.9.9.2 > 10.9.9.1: ICMP 10.9.9.2 protocol 253 unreachable, length 60
```

这条 ICMP 差错报文按 RFC 792 生成，类型 3（Destination Unreachable）、代码 2（Protocol Unreachable）。它的存在证明了完整的一条推理链：**对端内核接收报文后，依次校验版本号、首部长度、首部校验和、目的地址，全部通过并向上交付；直到"协议 253"这一层才发现没有对应的处理程序，于是回送差错并把原始首部嵌回。** 若首部任何一个字段填错，报文在更早的环节即被丢弃，这条 ICMP 根本不会产生。**它比"我看到包了"更有力，因为它证明对端真的解析了这份首部。**

#### 6.5.3　校验和的定量验证

6.4.4 节已从既有抓包推出"TTL 减 1 → 首部校验和增加 `0x0100`"。本程序的 `-i` 选项可固定标识，使两次运行除 TTL 外首部完全相同，从而把这条规律从推算变成实测（图 39）：

```
4500 0034 0064 0000 40fd 5355 0a09 0901 0a09 0902    校验和 0x5355   (TTL=64)
4500 0034 0064 0000 3ffd 5455 0a09 0901 0a09 0902    校验和 0x5455   (TTL=63)
```

两次首部仅第 9 字节由 `0x40` 变为 `0x3f`，校验和由 `0x5355` 变为 `0x5455`，差值恰为 `0x0100`。这与 6.4.4 节从帧 74 推出的规律完全一致，两节互相印证。

另有一条不期而至的旁证：三个报文标识依次为 `0x193b`、`0x193c`、`0x193d`，校验和依次为 `0x3a7e`、`0x3a7d`、`0x3a7c`——**标识每加 1，校验和恰好减 1**。这与"求和增加 1、取反后减少 1"的算术关系严格对应，从另一个方向证明了校验和函数确实是逐字正确计算的，而非碰巧对上某个值。

#### 6.5.4　为何必须具有管理员权限

实测已给出直接证据：普通用户执行时 `socket()` 返回 `EPERM`（图 32）。原因分三个层次：

**第一层，内核能力控制。** `SOCK_RAW` 需要 `CAP_NET_RAW` 能力，普通用户默认不持有。这是内核在网络子系统入口处做的权限检查，程序本身并未申请任何特权，是**内核不允许无特权进程直接操作网络层**。

**第二层，安全动机。** 原始套接字具备两项危险能力：一是**可指定任意源地址**，即具备伪造他人 IP 的能力，这是反射放大、会话劫持等攻击的基础；二是**可构造任意协议号**，绕过内核既有的 TCP/UDP 处理逻辑，直接向上层注入报文。若对普通用户开放，主机将失去对出站流量的基本约束。

**第三层，语义定位。** 需要强调的是，这不是"程序功能太强所以要更高权限"，而是"手工构造网络层报文这件事，本质上是在替内核行使职责"。内核把这道门设在 root，正是为了明确"谁有权定义网络层语义"。

## 七、遗留缺陷

### 7.1　只验证了提交环节，MX 中继未观测

公网投递在 6.2.2 节已打通（`queued as` + 收件箱实收），但整条投递链其实分两段：**客户端 → 服务商提交服务器（submission）** 与 **服务商之间按 MX 记录互相中继（relay）**。本实验只覆盖了前一段，后一段既抓不到包（在腾讯内部网络）、也无从干预，因此"邮件如何依据 MX 记录找到目标域"这一环节未获验证。

另外两处未覆盖：`PIPELINING` 虽然在 `EHLO` 应答中被服务器声明支持，但为逐条观察应答，全程未批量提交命令；25 端口的 `STARTTLS` 升级路径也未尝试，只用了 465 的隐含 TLS。

### 7.2　traceroute 仅观测到第一跳

受 5.6 节所述的宿主机栈重建影响，第 2 跳起全部 `* * *`，无法获得完整路径。虽以主动 TTL 设定与首跳 ICMP 差错作为替代证据，但"多跳递减"这一现象本身未能在本环境中直接观测。

### 7.3　双点抓包未实现

4.3 节选择了单点双向对照，因此"同一分组在收发两端"的严格对照缺失。宿主机 Npcap 安装失败（0x800700b7）是直接原因，深层原因是校园网策略与杀毒软件拦截驱动安装。

### 7.4　`ip_raw` 只实现了发送方向

程序用 `IPPROTO_RAW` 发送自定义协议号报文，但未实现接收路径（`recvfrom` 读取原始报文），也未测试 IP 分片与重组。分片测试需要构造大于 MTU 的载荷并观察 MF 位与片偏移，本次因载荷固定在 32 字节而未覆盖。

### 7.5　未涉及 IPv6

全部实验基于 IPv4，包括首部构造、校验和、TTL 与分片。IPv6 取消了首部校验和、改由上层负责，并将 TTL 改为 Hop Limit，语义有实质差别，本次未做对照。

### 7.6　邮件首部未按 RFC 2047 编码

6.2.2 节的 `Subject` 直接写入中文字节。按 RFC 5321，SMTP 首部应为 US-ASCII；非 ASCII 内容需按 RFC 2047 编码为 `=?UTF-8?B?…?=`，或依赖 `SMTPUTF8` 扩展（该服务器在 `EHLO` 中已声明支持）。本次实测 QQ 网页端显示正常，但这属于服务端宽容，不具普遍性——若收件方是只认 ASCII 的旧式客户端，主题会呈现为乱码。规范做法应在发信时显式编码。

## 八、小结

本次实验最有价值的七点认识：

1. **应用层协议是可手工构造的文本。** HTTP 与 SMTP 均由 ASCII 文本行构成，以 CRLF 分行、以空行或单行句点标志边界。手工构造报文与浏览器/邮件客户端的结果一致，说明应用层协议的全部"智能"都在报文结构与状态机的约定之中，而非客户端软件本身。

2. **三位状态码是协议状态机的显式表达。** SMTP 的 `220 → 250 → 334 → 235 → 250 → 354 → 250 → 221` 与 HTTP 的 `200` 属同一设计思想：首位数字表达结果类别（2 成功、3 中间态、4 暂时性失败、5 永久性失败）。两个细节值得注意：`354` 是唯一"同意继续但事务尚未完成"的中间状态，对应 DATA 阶段的双向握手；`334` 与 `235` 成对出现，且 `235` 专用于认证结果，与邮件事务的 `250` 刻意区分——协议用不同的成功码标明"这一步成功"与"整件事成功"不是一回事。

3. **TCP 的"三次"与"四次"是逻辑模型，报文数取决于实现。** 理论四段挥手在实测中因捎带确认合并为三段，说明协议规定的状态迁移次序是刚性的，但报文边界可由实现优化。

4. **TTL 是唯一可被路由器改写的 IP 首部字段。** 本次实验通过 IP 标识配对（`0xb963` 在发送端与差错报文内嵌副本中完全一致）确证了 TTL 归零丢弃机制，并定量验证了"TTL 减 1 → 校验和加 `0x0100`"的联动关系。

5. **虚拟化与代理会破坏网络层的可观测性。** 宿主机 Windows 栈重组回包后，TTL 被统一重置为 128、IP 标识连续递增，导致直接按 TTL 推算跳数失效。**结论必须建立在可交叉验证的证据链上**——这里最终是通过"标识连号"这一不依赖 TTL 的独立线索定位到问题根源的，而非接受一个看似合理却自相矛盾的数值。

6. **工具默认语义容易被忽视。** `smtp-sink` 默认丢弃邮件、`tcpdump -i any` 使用 SLL2 伪首部、`tcpdump -X` 默认不打印以太网头、`traceroute` 每跳发 3 个探测包——这些默认行为若不了解，轻则误判实验失败，重则得出错误结论。

7. **只有亲手构造一次，才知道内核承担了多少。** 应用层我们只写文本、传输层内核维护连接状态、网络层连 20 个首部字节都需自行填写，而内核保留的只是"是否允许你这么做"的判断权（`CAP_NET_RAW`）。

**反思。** 复盘整个过程，真正耗时的不在"把实验做出来"，而在"判断结果是否可信"。三次判断失误指向同一个毛病：**过早用了一个"讲得通"的解释收尾**。

SMTP 的 535 排查三轮后归因为"服务商风控"，听起来合理，直到第四轮换一个新授权码就通了——"码已作废"与"账号被风控"在应答文本上完全同形，仅靠排除客户端根本无法区分；TTL=128 一开始被当成"网络未经过路由器"，直到发现跨太平洋 170 ms 与 0 跳自相矛盾，才顺着 IP 标识连号查到宿主机栈重建；`s_client` 的 `RENEGOTIATING` 一开始被当成"服务器拒绝"，其实是整段粘贴丢掉了"等待应答"这个隐含同步点。

这三次都说明：**一个数值或一条报文本身不构成证据，能与其他独立观测量相互印证才构成证据；而一个讲得通的解释，尤其需要再找一个独立来源去证伪它。** 这与写代码时的体会一致——校验和是否写对，不能靠"看起来对"，要靠"标识增 1 则校验和减 1"这种可独立验算的关系来反证。

另一方面，本实验也暴露了自己对工具默认行为的忽视：`smtp-sink` 收下邮件直接丢弃、`tcpdump -X` 不显示链路层头、框架的 `-Weffc++` 把风格问题升级为编译错误。这些都不是"知识点"，而是"工具契约"——用之前先读一眼手册，比事后调试三小时划算得多。

若重做一次，我会把验证方案前置：在动手前先想清楚"这个结论用什么证据支撑、该证据会被什么因素污染"，而不是先跑通再找证据。本次 TTL 部分之所以走了弯路，正是因为验证方案是在拿到异常数据之后才补的。

```cpp
/**
 * ip_raw.cc -- 实验一 5.3.5：原始套接字手工构造 IPv4 首部并发送自定义协议号数据报
 *
 * 编译：cmake --build build --target ip_raw -j4
 * 运行：sudo ./build/apps/ip_raw <目标IP> [-n 次数] [-l 载荷字节] [-t TTL] [-p 协议号] [-s 源IP]
 * 示例：sudo ./build/apps/ip_raw 192.168.159.1 -n 3 -l 32 -t 64 -p 253
 *
 * 四个设计要点（对应报告 6.5 节的原理分析）：
 *   1. socket(AF_INET, SOCK_RAW, IPPROTO_RAW)：Linux 上该组合隐含开启 IP_HDRINCL，
 *      内核不再替报文生成 IP 首部，20 字节首部完全由本程序填写——这是"亲手构造"的前提。
 *   2. 协议号默认 253：RFC 3692 将 253/254 保留给"实验与测试"用途，不与 TCP(6)/UDP(17)
 *      等真实协议冲突，抓包时用 ip.proto == 253 一筛即得本程序的报文。
 *   3. 首部校验和按 RFC 1071 的 16 位反码和自行计算，不依赖内核补零机制，
 *      因此抓包中看到的校验和是程序算出的值，可与手算结果逐位对照。
 *   4. 源地址不硬编码：先用一个 UDP 套接字对目标做 connect（不发包，只查路由表），
 *      再从 getsockname 取本机出口地址，避免换网络环境后源码失效。
 */

// ---- 本实验使用的常量 -------------------------------------------------------
// 协议号 253：RFC 3692 "Assigning Experimental and Testing Numbers" 划定的实验用途号，
// 不与任何注册协议冲突，抓包过滤器 ip.proto == 253 可精确定位本程序的报文。
constexpr uint8_t DEFAULT_PROTOCOL = 253;
constexpr uint8_t DEFAULT_TTL = 64;
constexpr int DEFAULT_COUNT = 3;
constexpr int DEFAULT_PAYLOAD = 32;

constexpr size_t IP_HEADER_LEN = 20;      // IPv4 首部无选项时固定 20 字节
constexpr int MAX_PAYLOAD = 1400;         // 小于 MTU 1500 - 20，避免触发 EMSGSIZE 分片
constexpr int MAX_COUNT = 100;

// ---- IPv4 首部结构（RFC 791）------------------------------------------------
// 用 pragma pack 关闭编译器填充，保证 sizeof 恰好 20 字节，与线上格式逐字节对应。
#pragma pack( push, 1 )
struct IpHeader
{
  uint8_t ver_ihl;    // [0] 版本(高 4 位) + 首部长度(低 4 位，单位为 4 字节)
  uint8_t tos;        // [1] 区分服务，本实验恒 0
  uint16_t tot_len;   // [2-3] 总长度 = 首部 + 载荷，网络字节序
  uint16_t id;        // [4-5] 标识，同一数据报的多个分片共享此值
  uint16_t frag_off;  // [6-7] 标志(高 3 位) + 片偏移(低 13 位)，本实验置 0
  uint8_t ttl;        // [8] 生存时间，每经一台路由器减 1，为 0 则丢弃
  uint8_t protocol;   // [9] 上层协议号
  uint16_t check;     // [10-11] 首部校验和，仅覆盖首部 20 字节
  uint32_t saddr;     // [12-15] 源地址
  uint32_t daddr;     // [16-19] 目的地址
};
#pragma pack( pop )

static_assert( sizeof( IpHeader ) == IP_HEADER_LEN, "IPv4 首部必须恰好 20 字节" );

// ---- 命令行选项 -------------------------------------------------------------
// 注意：每个成员都带 {} 或默认值（NSDMI）。框架启用了 -Weffc++ 与 -Werror，
// 该规则要求所有成员都必须显式初始化，否则编译直接失败：
//   error: 'Options::target' should be initialized in the member initialization list
struct Options
{

  string source {};                  // 源 IP，空表示自动探测
  int count { DEFAULT_COUNT };       // 发送个数
  int payload_len { DEFAULT_PAYLOAD }; // 载荷字节数
  int ttl { DEFAULT_TTL };           // 生存时间
  int protocol { DEFAULT_PROTOCOL }; // 协议号
  int id { -1 };                     // 固定标识值，-1 表示按进程号自动生成
};

       << "  -t <ttl>        生存时间，1..255（默认 " << static_cast<int>( DEFAULT_TTL ) << "）\n"

}

// 把字符串转成整数，非法输入直接抛异常（比 atoi 静默返回 0 更容易定位误用）
static int parse_int( const string& text, const string& opt )
{
  size_t used = 0;
  int value = 0;
  try {
    value = stoi( text, &used );
  } catch ( const exception& ) {
    throw invalid_argument( "选项 " + opt + " 需要一个整数，收到 \"" + text + "\"" );
  }
  if ( used != text.size() ) {
    throw invalid_argument( "选项 " + opt + " 的取值 \"" + text + "\" 含非数字字符" );
  }
  return value;
}

static Options parse_args( int argc, char* argv[] )
{
  Options opts;
  for ( int i = 1; i < argc; ++i ) {
    const string arg { argv[i] };
    const bool has_next = ( i + 1 < argc );

    auto take_value = [&]( const string& name ) -> string {
      if ( !has_next ) {
        throw invalid_argument( "选项 " + name + " 缺少取值" );
      }
      return string { argv[++i] };
    };

    if ( arg == "-h" || arg == "--help" ) {
      show_usage( argv[0] );
      exit( EXIT_SUCCESS );
    } else if ( arg == "-n" ) {
      opts.count = parse_int( take_value( arg ), arg );
    } else if ( arg == "-l" ) {
      opts.payload_len = parse_int( take_value( arg ), arg );
    } else if ( arg == "-t" ) {
      opts.ttl = parse_int( take_value( arg ), arg );
    } else if ( arg == "-p" ) {
      opts.protocol = parse_int( take_value( arg ), arg );
    } else if ( arg == "-i" ) {
      opts.id = parse_int( take_value( arg ), arg );
    } else if ( arg == "-s" ) {
      opts.source = take_value( arg );
    } else if ( !arg.empty() && arg[0] == '-' ) {
      throw invalid_argument( "未知选项 " + arg );
    } else if ( opts.target.empty() ) {
      opts.target = arg;
    } else {
      throw invalid_argument( "只能指定一个目的地址，多余参数：" + arg );
    }
  }

  if ( opts.target.empty() ) {
    throw invalid_argument( "缺少目的地址" );
  }
  if ( opts.count < 1 || opts.count > MAX_COUNT ) {
    throw invalid_argument( "次数 -n 需在 1.." + to_string( MAX_COUNT ) + " 之间" );
  }
  if ( opts.payload_len < 0 || opts.payload_len > MAX_PAYLOAD ) {
    throw invalid_argument( "载荷长度 -l 需在 0.." + to_string( MAX_PAYLOAD ) + " 之间" );
  }
  if ( opts.ttl < 1 || opts.ttl > 255 ) {
    throw invalid_argument( "TTL -t 需在 1..255 之间" );
  }
  if ( opts.protocol < 0 || opts.protocol > 255 ) {
    throw invalid_argument( "协议号 -p 需在 0..255 之间" );
  }
  if ( opts.id > 65535 ) {
    throw invalid_argument( "标识 -i 需在 0..65535 之间" );
  }
  return opts;
}

// ---- 16 位反码和校验和（RFC 1071）-------------------------------------------
// 算法分四步：① 按 16 位大端切字累加；② 奇数长度末字节左移 8 位补零参与；
// ③ 进位回卷（高 16 位加到低 16 位，重复至不再溢出）；④ 按位取反。
// 只用首部 20 字节，不覆盖载荷——这是 IP 层"尽力而为"的一个侧面：
// 首部错了整包丢弃，载荷错了交给上层自己校验（TCP/UDP 各自有校验和）。
static uint16_t checksum16( const void* data, size_t len )
{
  const auto* bytes = static_cast<const uint8_t*>( data );
  uint32_t sum = 0;

  for ( size_t i = 0; i + 1 < len; i += 2 ) { // ① 两个字节合成一个 16 位大端字
    sum += ( static_cast<uint32_t>( bytes[i] ) << 8 ) | bytes[i + 1];
  }
  if ( ( len & 1U ) != 0U ) {                 // ② 奇数长度：末字节当高 8 位
    sum += static_cast<uint32_t>( bytes[len - 1] ) << 8;
  }
  while ( ( sum >> 16 ) != 0U ) {             // ③ 进位回卷
    sum = ( sum & 0xFFFFU ) + ( sum >> 16 );
  }
  return static_cast<uint16_t>( ~sum & 0xFFFFU ); // ④ 取反
}

// ---- 探测本机出口地址 --------------------------------------------------------
// 技巧：建一个 UDP 套接字并 connect 到目标。UDP connect 不发任何报文，
// 只是让内核查一次路由表并把"默认出口地址"绑定上去，随后 getsockname 即可读出。
// 这样换网络（NAT 网段变化、桥接、真机）都不用改源码，比硬编码 192.168.159.128 稳妥。
static in_addr probe_source_addr( const in_addr& dst )
{
  const int probe = socket( AF_INET, SOCK_DGRAM, 0 );
  if ( probe < 0 ) {
    throw runtime_error( string { "创建探测套接字失败: " } + strerror( errno ) );
  }

  sockaddr_in peer {};
  peer.sin_family = AF_INET;
  peer.sin_addr = dst;
  peer.sin_port = htons( 9 ); // discard 端口，仅为满足 connect 参数要求

  in_addr local_addr {};
  if ( connect( probe, reinterpret_cast<const sockaddr*>( &peer ), sizeof( peer ) ) == 0 ) {
    sockaddr_in local {};
    socklen_t len = sizeof( local );
    if ( getsockname( probe, reinterpret_cast<sockaddr*>( &local ), &len ) == 0 ) {
      local_addr = local.sin_addr;
    }
  }
  close( probe );

  if ( local_addr.s_addr == 0 ) {
    throw runtime_error( "无法探测本机出口地址，请用 -s 手工指定源 IP" );
  }
  return local_addr;
}

// ---- 输出辅助 ---------------------------------------------------------------
static string ip_to_string( const in_addr& addr )
{
  char buf[INET_ADDRSTRLEN] = {};
  if ( inet_ntop( AF_INET, &addr, buf, sizeof( buf ) ) == nullptr ) {
    return "?";
  }
  return buf;
}

static void dump_hex( const string& label, const uint8_t* data, size_t len )
{
  cout << label;
  for ( size_t i = 0; i < len; ++i ) {
    if ( i != 0 && i % 4 == 0 ) {
      cout << ' ';
    }
    cout << hex << setw( 2 ) << setfill( '0' ) << static_cast<int>( data[i] );
  }
  cout << dec << setfill( ' ' ) << '\n';
}

static void print_header( const IpHeader& ip, size_t payload_len )
{
  const int ver = ip.ver_ihl >> 4;
  const int ihl = ( ip.ver_ihl & 0x0FU ) * 4;
  const uint16_t tot = ntohs( ip.tot_len );
  const uint16_t id = ntohs( ip.id );
  const uint16_t frag = ntohs( ip.frag_off );

  cout << "  +----------------- IP 首部逐字段 ----------------+\n"
       << "  | 版本            " << ver << "  (IPv" << ver << ")\n"
       << "  | 首部长度        " << ihl << " 字节 (" << ( ip.ver_ihl & 0x0FU ) << " x 4)\n"
       << "  | 区分服务 TOS   0x" << hex << setw( 2 ) << setfill( '0' ) << static_cast<int>( ip.tos ) << dec
       << setfill( ' ' ) << "\n"
       << "  | 总长度          " << tot << " 字节 (首部 " << ihl << " + 载荷 " << payload_len << ")\n"
       << "  | 标识 ID        0x" << hex << setw( 4 ) << setfill( '0' ) << id << dec << setfill( ' ' ) << " (" << id << ")\n"
       << "  | 标志/片偏移    0x" << hex << setw( 4 ) << setfill( '0' ) << frag << dec << setfill( ' ' )
       << " (DF=" << ( ( frag & 0x4000U ) != 0U ? 1 : 0 ) << " MF=" << ( ( frag & 0x2000U ) != 0U ? 1 : 0 )
       << " 偏移=" << ( frag & 0x1FFFU ) << ")\n"
       << "  | 生存时间 TTL   " << static_cast<int>( ip.ttl ) << "\n"
       << "  | 协议号          " << static_cast<int>( ip.protocol ) << "\n"
       << "  | 首部校验和      0x" << hex << setw( 4 ) << setfill( '0' ) << ntohs( ip.check ) << dec << setfill( ' ' ) << "\n";

  in_addr s {};
  in_addr d {};
  s.s_addr = ip.saddr;
  d.s_addr = ip.daddr;
  cout << "  | 源地址          " << ip_to_string( s ) << "\n"
       << "  | 目的地址        " << ip_to_string( d ) << "\n"
       << "  +-----------------------------------------------+\n";
}

// ---- 主流程 -----------------------------------------------------------------
int main( int argc, char* argv[] )
{
  try {
    if ( argc <= 0 ) {
      abort(); // 与框架其它 app 保持一致：不允许 access argv[0] when argc <= 0
    }
    if ( argc == 1 ) {
      show_usage( argv[0] );
      return EXIT_FAILURE;
    }

    const Options opts = parse_args( argc, argv );

    // 1) 解析目的地址（同时充当格式校验，非法 IP 在这里就被拦下）
    sockaddr_in dst {};
    dst.sin_family = AF_INET;
    if ( inet_pton( AF_INET, opts.target.c_str(), &dst.sin_addr ) != 1 ) {
      throw invalid_argument( "目的地址不是合法的 IPv4 点分十进制串: " + opts.target );
    }

    // 2) 确定源地址
    in_addr src {};
    if ( !opts.source.empty() ) {
      if ( inet_pton( AF_INET, opts.source.c_str(), &src ) != 1 ) {
        throw invalid_argument( "源地址不是合法的 IPv4 点分十进制串: " + opts.source );
      }
    } else {
      src = probe_source_addr( dst.sin_addr );
    }

    // 3) 创建原始套接字。IPPROTO_RAW 在 Linux 上隐含 IP_HDRINCL：
    //    内核认为"首部已由用户提供"，只做转发，不再生成任何 IP 字段。
    //    普通用户执行会在此返回 EPERM，因为 SOCK_RAW 需要 CAP_NET_RAW 能力。
    const int fd = socket( AF_INET, SOCK_RAW, IPPROTO_RAW );
    if ( fd < 0 ) {
      if ( errno == EPERM ) {
        cerr << "socket(SOCK_RAW) 被拒绝: 需要管理员权限。请用 sudo 重新执行：\n"
             << "  sudo " << argv[0] << " " << opts.target << "\n";
      } else {
        cerr << "创建原始套接字失败: " << strerror( errno ) << "\n";
      }
      return EXIT_FAILURE;
    }

    // 显式置 IP_HDRINCL：对 IPPROTO_RAW 内核已默认开启，这里再设一次是为了让代码意图可见；
    // 万一某平台已默认且拒绝重复设置，按提示降级继续，不致命。
    const int one = 1;
    if ( setsockopt( fd, IPPROTO_IP, IP_HDRINCL, &one, sizeof( one ) ) < 0 ) {
      cerr << "note: setsockopt(IP_HDRINCL) 返回 " << strerror( errno )
           << "（IPPROTO_RAW 已默认开启，继续执行）\n";
    }

    const size_t total_len = IP_HEADER_LEN + static_cast<size_t>( opts.payload_len );
    cout << "原始套接字已就绪: fd=" << fd << "  协议号=" << opts.protocol << "  TTL=" << opts.ttl << "\n"
         << "源 " << ip_to_string( src ) << " -> 目的 " << opts.target << "  共 " << opts.count << " 个报文，"
         << "每个 " << total_len << " 字节（首部 20 + 载荷 " << opts.payload_len << "）\n"
         << "提示: 发送期间在对端执行 tcpdump -n -i 任意接口 'ip proto " << opts.protocol
         << "'，或在 Wireshark 用过滤条件 ip.proto == " << opts.protocol << "\n\n";

    // 标识字段的起始值取进程号低 16 位，逐个递增，便于在对端抓包时区分本进程的报文
    const uint16_t base_id = static_cast<uint16_t>( getpid() & 0xFFFF );

    vector<uint8_t> packet( total_len, 0 );

    for ( int i = 0; i < opts.count; ++i ) {
      // 4) 逐字段填写 IP 首部（字段顺序与 RFC 791 一致，偏移见 struct 注释）。
      //    这里用对齐的局部对象，而不是把 vector 缓冲区强转成 IpHeader*：
      //    vector<uint8_t> 只保证 1 字节对齐，强转成含 uint16/uint32 成员的结构体，
      //    在 x86 上能跑（仅降速），在 ARM 等严格对齐平台上会直接触发异常。
      IpHeader ip {};

      // 标识：-i 指定时用固定值（便于跨运行只改 TTL 对比校验和），否则按进程号递增
      const uint16_t this_id = ( opts.id >= 0 ) ? static_cast<uint16_t>( opts.id )
                                                : static_cast<uint16_t>( base_id + i );

      ip.ver_ihl = 0x45; // 版本 4（高 4 位）+ 首部长度 5（低 4 位，5 x 4 = 20 字节）
      ip.tos = 0x00;     // 区分服务，本实验不使用 QoS
      ip.tot_len = htons( static_cast<uint16_t>( total_len ) ); // 含首部的总长度，网络序
      ip.id = htons( this_id );                                 // 标识，同一数据报的各分片共享
      ip.frag_off = htons( 0x0000 );                            // DF=0 MF=0 偏移=0，允许分片
      ip.ttl = static_cast<uint8_t>( opts.ttl );                // 生存时间由发送方设定
      ip.protocol = static_cast<uint8_t>( opts.protocol );      // 自定义协议号
      ip.check = 0;                                             // 先置 0 再计算，否则结果错
      ip.saddr = src.s_addr;
      ip.daddr = dst.sin_addr.s_addr;

      // 载荷：填一段可读文本，抓包时在十六进制区能直接认出本程序的报文；
      // 若载荷长于文本则余下保持 0，短于文本则截断。
      const string text = "CS144-Minnow ip_raw proto=" + to_string( opts.protocol ) + " seq="
                          + to_string( i + 1 ) + "/" + to_string( opts.count );
      const size_t copy_len = min( text.size(), static_cast<size_t>( opts.payload_len ) );
      if ( copy_len > 0 ) {
        memcpy( packet.data() + IP_HEADER_LEN, text.data(), copy_len );
      }

      // 5) 计算并回填首部校验和。此刻 ip.check 仍为 0，符合"计算前该字段须置零"的前提；
      //    算完再整块拷进报文缓冲，保证线上字节与打印内容完全一致。
      ip.check = htons( checksum16( &ip, IP_HEADER_LEN ) );
      memcpy( packet.data(), &ip, IP_HEADER_LEN );

      // 6) 发送。IPPROTO_RAW 下首部里的 daddr 才是权威，但 sockaddr 仍需填写，
      //    内核会用 sin_addr 做一次合法性检查（全 0 会被判 EINVAL）。
      const ssize_t sent = sendto( fd,
                                   packet.data(),
                                   packet.size(),
                                   0,
                                   reinterpret_cast<const sockaddr*>( &dst ),
                                   sizeof( dst ) );
      if ( sent < 0 ) {
        cerr << "第 " << ( i + 1 ) << " 个报文发送失败: " << strerror( errno ) << "\n";
        if ( errno == EMSGSIZE ) {
          cerr << "  提示: 载荷过大超过链路 MTU，请用 -l 减小长度\n";
        }
        close( fd );
        return EXIT_FAILURE;
      }

      cout << "========== 报文 " << ( i + 1 ) << "/" << opts.count << "  已发出 " << sent << " 字节 ==========\n";
      dump_hex( "  首部字节: ", packet.data(), IP_HEADER_LEN );
      cout << "  " << "载荷文本: ";
      for ( size_t k = 0; k < copy_len; ++k ) {
        cout << static_cast<char>( packet[IP_HEADER_LEN + k] );
      }
      cout << "\n";
      print_header( ip, static_cast<size_t>( opts.payload_len ) );
      cout << "\n";

      if ( i + 1 < opts.count ) {
        this_thread::sleep_for( chrono::seconds( 1 ) ); // 间隔 1 秒，便于抓包时看清逐个到达
      }
    }

    close( fd );

    cout << "全部 " << opts.count << " 个报文发送完毕。\n"
         << "核对要点：\n"
         << "  1. 对端报文首部 Protocol 应为 " << opts.protocol << "（不是 TCP 6 / UDP 17）；\n"
         << "  2. 对端看到的 TTL 与上面打印的一致（同一广播域内转发不减 TTL）；\n"
         << "  3. 十六进制首部的前 20 字节应与“首部字节”一行逐字节相同。\n";
  } catch ( const exception& e ) {
    cerr << "错误: " << e.what() << "\n";
    return EXIT_FAILURE;
  }

  return EXIT_SUCCESS;
}
```
